# @rafflex/dev

```sh
npx @rafflex/dev@latest
```

* It sets up a workspace in a new `rafflex` folder (or opens the one you are in) and opens the Rafflex app in your browser. It asks nothing.
* The app shows every game and block you are building, previews each one in every play scenario, and tests it with one click.
* It hands every next step to your AI as a ready made prompt, so you never need a terminal again. Needs Node 20 or newer.

The full reference lives on the marketplace, so it always matches the rules in force:

* [docs/dev-kit.md](https://marketplace.rafflex.io/docs/dev-kit.md): the workspace, every command and its `--json` shape, the sync loop, and the public rule endpoints
* [llms.txt](https://marketplace.rafflex.io/llms.txt): everything an AI assistant needs to build for the marketplace

## Workspace

```
rafflex/
  rafflex.json        {"workspace": 1}
  AGENTS.md           how an AI works here (CLAUDE.md imports it)
  .rafflex/           the rules and Playwright cache (git ignored)
  games/
    spin-to-win/
      product.json    type, slug, title, version, last known remote state and feedback (written by the kit)
      template.twig
      options.json    option overrides
      listing.md      description, documentation, install notes; categories, tags, video in the frontmatter
      CHANGELOG.md    release notes, Unreleased on top
      assets/
      listing/        cover.png (or .jpg, .webp) and screenshots/, shown in filename order; committed and pushed
      tests/          your own browser specs (optional, committed, never pushed)
      .results/       screenshots, the last test run, and verify.json (git ignored, never pushed)
  blocks/
    winner-wall/
```

The layout is fixed. `npx @rafflex/dev` outside a workspace (or `init` in an empty folder) creates it, with a git repository and a first commit when git is installed; `new` adds a product folder.

## Commands

Every command takes `--json` and exits 0 on success, 1 when a check finds a blocking problem or a command is refused, and 2 when it cannot run. A refused command prints `{"error": "..."}` with `--json`; `push`, `synced`, `release`, and a usage error (an unknown command or missing arguments) print `{"error": {"code": "...", "message": "..."}}` instead, with `issues` when the marketplace refused a push. A `<product>` is its slug, folder name, or path (`games/spin-to-win`), and defaults to the product folder you are in. After a first push renamed a folder to its slug, the old path still finds it, with a note saying where it is now.

| Command | What it does |
| --- | --- |
| `npx @rafflex/dev init` | Creates the workspace in this folder. Refused inside an existing one. |
| `npx @rafflex/dev new <game\|block> "<title>"` | Adds a product folder named after the title, from the type's starter template, at version 1.0.0. |
| `npx @rafflex/dev [--port N] [--no-open]` | Starts the Rafflex app for the whole workspace (port 5173, or the next free one) and opens the product you are in, or Home anywhere else. Outside a workspace it first sets one up in a new `rafflex` folder here, asking nothing. `npx @rafflex/dev dev <product>` opens a named product. See [The app](#the-app). |
| `npx @rafflex/dev format [<product>...\|--all] [--check]` | Formats templates in the house style (below). `--check` reports without writing. JSON: `{product, formatted, changed, written, error}`, or `{passed, products: [...]}` for several. |
| `npx @rafflex/dev check [<product>...\|--all]` | Renders every scenario headlessly and runs the rules, then the lint warnings and a format check. Outside a product folder it checks every product. `--play-count N` must be within the platform's range (1 to 25 today, published in `contexts.json`). `--json` prints one product's result, or `{passed, products: [...]}` for several. |
| `npx @rafflex/dev test [<product>...\|--all] [--install]` | The browser tests (below). Without Playwright it prints the install command and skips. `--install` installs Playwright and Chromium into `.rafflex/playwright` (about 100 MB; the AI asks first). JSON: `{product, passed, skipped, reason, install, issues, runs, playthrough, creator_tests, results}`. |
| `npx @rafflex/dev capture <product> [--force]` | Writes a cover image (1200 by 600, the shape of the marketplace's product cards) and screenshots into `listing/` from the browser run when it has none: a game ready to play, after a win, and after a loss, at desktop and phone widths; a block at both widths. It never replaces a cover or screenshots already there unless `--force` is given. Without Playwright it prints the install command and skips, as `test` does. JSON: `{product, captured: [{path, width, height, size}], skipped, reason, install}`. |
| `npx @rafflex/dev verify [<product>...\|--all]` | `format`, then `check`, then `test` when Playwright is installed: the one command to run before every push. JSON: `{product, ready, browser_tests, format, check, test, issues, blocking, warnings, submission, note}`, or `{ready, products: [...]}`. Exits 1 when not ready. `submission` is `{ready, missing: [{key, message, fix?}]}`: what review still needs (a description, a category, a cover image, a screenshot, release notes once a version is live, and listing limits), with the marketplace's own messages. It never changes `ready`, because a draft can be pushed without them. |
| `npx @rafflex/dev status [<product>]` | Offline: each product's version, its remote state from the last sync, what changed locally since (`changes.listing_images: {cover, screenshots}` counts listing images to upload), `submission` as in `verify`, and `feedback` as the last sync recorded it: `{review: {version, decision, notes, decided_at, failing_checks}, open_bug_reports, unanswered_questions, statistics: {installs, sales, rating, ratings_count}}` (null before any). The prose prints the review decision with its notes, and the counts. It also refreshes `AGENTS.md` when the file is still the kit's generated copy and the marketplace's guidance changed (`agents_md` in the JSON: `current`, `updated`, `customised`, or `unknown`). |
| `npx @rafflex/dev version <product> <patch\|minor\|major\|x.y.z>` | Sets the version being worked on. Refused while that version is in review. |
| `npx @rafflex/dev import <bundle> [--force]` | Writes a product from an `export_product` bundle (a file, its URL, or `-` for standard input) into `<type folder>/<slug>`, downloading each media file and checking its SHA-256. An existing product folder is replaced only with `--force`; the refusal lists its local changes. A bundle whose slug, type, media tag, or media file name is not a plain name is refused before anything is written, and every write stays inside the product folder. The bundle download gives up after 30 seconds and each file after 2 minutes, writing nothing. |
| `npx @rafflex/dev plan <product>` | Runs `verify` first; while anything blocks, it says "not ready to push", lists the blocking issues, and exits 1 (`ready` and `verify: {ready, browser_tests, blocking_issues, warning_count}` in the JSON). Then the push plan as data: whether the template, options, or listing changed since the last sync, each new or changed asset (path, tag, kind, size, MIME type, SHA-256, and the library name for an approved library, matched by its hash rather than its tag), `removed_assets` for media on the marketplace with no file in `assets/` (the kit never removes media; the AI asks the creator to remove it in the browser), the Unreleased release notes, and `stale_remote` when the last sync is missing or over a day old. `listing_images` is `{cover, screenshots, removed_screenshots}`: the cover (`change` `new` or `changed`) and each new screenshot as `{path, sha256, size, mime_type, change}`, compared with the marketplace by SHA-256, and the hashes of screenshots on the marketplace that `listing/screenshots/` no longer holds (only when it holds any). `refusals` lists changed files the marketplace will not take again (`asset_locked`: a submitted or published version uses the file, so save the change under a new name), and `submission` is as in `verify`. `suggested_version` is `{version, bump, reason}`, or null: the bump the platform would suggest against the live version's options (major when an option it reads is gone, minor when one is added, patch otherwise), and the prose warns when the version in progress is lower. Without `--json` it says to call `request_sync` and run `push`, then lists the marketplace tools to call in order for an AI app without a shell, with `request_media_upload` and its purpose (`cover` or `screenshot`) for each listing image. |
| `npx @rafflex/dev push <product> <sync_url>` | Pushes a product in one command through the sync link `request_sync` returns. It reads the product's state from the link and refuses (`wrong_link`) a link for an existing product when the folder was never pushed. It refuses (`conflict`) when the draft changed on the marketplace since the last sync (another draft version, or another revision of the same draft) and the folder's template or options differ from it. It runs `verify`, reusing `.results/verify.json` only when no file in the folder was added, changed, or deleted since and the platform's rules and the kit are the ones it was made with, and refuses while anything blocks. Then it sends only what `plan` lists: the template, option overrides, version, release notes, listing, approved libraries, and each new file, uploaded to the link the marketplace answers with (in batches of the marketplace's `max_files_per_batch`). Tags compare the way the marketplace matches them (by slug, so `WHEEL` and `wheel` are one tag). A product never pushed is created, and its folder renamed to the slug. When `listing/screenshots/` holds files, screenshots on the marketplace that it no longer holds are removed. It then reads the product again, records it as `synced` does, and commits the product folder as "Push spin-to-win 1.3.0 (draft revision 8)", or "Push spin-to-win 1.3.0 (draft revision 8, 2 files not uploaded)" when some files did not upload or were refused as locked: those files stay out of the commit, so they still show as changes and `restore last-push` treats them as unpushed. A push that changed nothing on the marketplace makes no Push commit. `check` leaves out `unknown_file_tag` warnings for files the push uploaded or attached. JSON: `{product, renamed_from, pushed, created, nothing_to_push, slug, version, revision, changed: {template, options, listing}, uploaded: [{path, purpose, tag}], attached: [{library, tag}], removed_screenshots, check, submission, suggested_version, feedback, not_uploaded, refusals, notes, git, link, commit_message, error?: {code, message, issues?, retry_after_seconds?}}`. An issue about a file to upload carries `path`, the file in the product folder. Exits 1 when refused for a reason the AI can fix or wait out (`not_ready`, `conflict`, `in_review`, `wrong_link`, the marketplace's `validation_failed` with its `issues`, `upload_failed`, `rate_limited` with the wait, `forbidden`) and 2 when it cannot run (`no_link`, `invalid_link`, `expired`, `unreachable`, `cannot_run`, `unexpected_response`, `unsupported`). A file that did not upload is named; the draft is already written, so the state that landed is recorded and a second `push` sends only what is still missing. |
| `npx @rafflex/dev synced <product> [<sync_url>]` | Records the product's marketplace state in `product.json`: from a sync link, with its `feedback`, or from a `get_product` result on standard input (the structured content or the whole tool result) for an AI app without a shell. The first sync records the slug and renames the folder to it; the version follows the server's draft. When the draft revision or version changed it commits the product folder: "Push spin-to-win 1.3.0 (draft revision 7)" when the folder holds what the marketplace now has, and "Sync spin-to-win (draft revision 7)" when the draft changed elsewhere (in the studio). When only the rest of the recorded state changed (the draft went into review, a review decision, locked media, feedback) it commits `product.json` alone as "Sync spin-to-win (in review)" or similar. A state that differs only in its sync time is not written, so the tree stays clean. Refusals use `error: {code, message}` (`not_created`, `wrong_link`, `wrong_product`, `no_link`, `invalid_input`, and the link's codes). |
| `npx @rafflex/dev release <product> [<sync_url>]` | After `submit_for_review`: moves the Unreleased notes under `## <version> (submitted <date>)`, starts a fresh Unreleased, marks the draft as in review in the recorded state (so the app shows In review without another sync), commits the product folder, and tags `<slug>@<version>`. With a sync link it first reads the marketplace, and unless that version is in review (or already released) it changes nothing (no changelog edit, commit, or tag) and exits 1 with `not_submitted`, saying to call `submit_for_review` first; otherwise it records the fresh state instead of marking it. A version submitted again after changes were requested adds to its existing section; its tag is left where it is. JSON: `{product, slug, version, heading, merged, notes, in_review, git}`; refusals use `error: {code, message}` (`not_submitted`, `not_created`, `wrong_link`, `no_changelog`, `no_notes`, and the link's codes). |
| `npx @rafflex/dev restore <product> last-push [--yes]` | Discards unpushed work: lists what would be lost, and with `--yes` returns the product folder to its last confirmed push (the kit's newest Push, Release, Import, or Revert commit, never a Sync), leaving `tests/` alone. A push where some files did not upload is a restore point, and those files count as unpushed. Without git it explains the `export_product` and `import --force` route. Going back to an earlier shipped version is `revert_to_version` on the marketplace. |

## The sync loop

The kit never signs in and holds no secret. When the creator says push, their AI asks the marketplace for a short lived sync link with its `request_sync` tool and hands it to the kit as an argument. The link works for 15 minutes, for one product (or one new product), and the kit never writes it down.

1. **Push.** `request_sync` (with the product's slug, or none for a new product) returns `sync_url`. `npx @rafflex/dev push <product> "<sync_url>"` verifies, sends only what changed, uploads the files, and records the result. The template never passes through the AI.
2. **Submit.** When the creator says go, the AI calls `submit_for_review`, then runs `npx @rafflex/dev release <product>` (or `release <product> "<sync_url>"` to record the marketplace's state too; it refuses while the version is not in review).
3. **Read the answer.** `request_sync`, then `npx @rafflex/dev synced <product> "<sync_url>"` records the review decision, the reviewer's notes, the open bug report and unanswered question counts, and the headline numbers. The app shows them, and `status --json` carries them as `feedback`.
4. **Bring a product local.** `export_product` returns a link to a bundle; `npx @rafflex/dev import "<bundle_url>"` writes the product folder (quote the URL: it holds `&`).

`plan <product>` shows what a push would send, as data. An AI app without a shell uses the tool by tool route instead: read the product with `get_product` and pipe it to `npx @rafflex/dev synced <product>`, call the tools `plan` lists (`create_product` the first time, `update_draft`, `update_product_details`, `request_media_upload` or `attach_approved_library`), then read the product again and pipe it to `synced`.

`import` commits the product as "Import spin-to-win from the marketplace" (or "Revert spin-to-win to 2.0.0 as 3.0.1" after `revert_to_version`), and `push` as "Push spin-to-win 1.3.0 (draft revision 8)" (with ", 2 files not uploaded" when some did not). The kit only ever commits the product concerned; the AI commits its own verified changes in between.

When the server's draft changed since your last sync (the creator edited it in the studio), `push` refuses. Commit first so git keeps your local work, then export and import it again, and apply your change on top.

## The quality loop

`npx @rafflex/dev verify <product>` before every push. The preview runs `check` on every save, and `plan` runs `verify` first, so the loop also runs when nobody asks.

* **Format.** One house style: Prettier over the HTML, inline CSS, and inline JavaScript with a fixed configuration pinned with the kit. Every Twig region is masked before formatting and restored byte for byte, and the formatted template must render the same page as the original in every scenario, or it is left untouched. `check` warns `unformatted`.
* **Lint (warnings, never blocking).** ESLint on every inline script (undefined and unused variables, unreachable code, `==`), Alpine attributes that read state no `x-data` declares (`alpine_state`), and an HTML validator (`markup`: unclosed or misnested elements, duplicate ids, images without `alt`). The platform's own game warnings come from its rules: `game_twig_logic` (a game uses only `{{ value|json }}`, `{{ files['tag'] }}`, `{{ settings.* }}`, and a simple `{% if %}`) and `playthrough_hooks_missing`.
* **Listing and media (blocking).** `listing_invalid`: `listing.md` does not parse, a section, the video link, or a tag is over the marketplace's limits, the video link is not a web address, a category is not on the marketplace (names such as `"Instant Win"` work as well as ids), or a cover or screenshot is the wrong type, too large, not what its extension says, or one too many. For the files a push would upload: `asset_filename` (a name the upload refuses, with the name to use), `asset_duplicate` (two files with the same upload name or tag), `asset_capacity` (more media than a product's library holds), and `asset_content_mismatch` (a PNG, JPEG, WebP, GIF, MP3, or GLB whose content is something else). Each limit comes from the marketplace's rules and is skipped when they do not publish it.
* **Options.** The kit infers the options a template reads exactly as the platform does (field types, labels, defaults, choices, repeaters, the Categories filter), proven by a fixture suite recorded from the platform. `check` reports the platform's `option_warning`s, and also warns when this version stops reading an option the live version reads (sites lose the value, so it is a major release). `options.json` is checked as the marketplace checks it on a push: a label, help, or choice of the wrong type, over the published limits (`rules.option_overrides`), or matching a banned pattern blocks (`option_override_invalid`), because the marketplace refuses the whole push; an entry it would silently drop (a key the template never reads, choices on an option that is not text, a choice with a comma) is an `option_warning`. Every scenario is rendered once more with every option set as a buyer may set it (long text, a large number, toggles flipped, each choice in turn, a full repeater, a ticked category); a render error then blocks (`option_render_error`).
* **Test (Playwright, optional).** Every scenario at phone, tablet, and desktop widths in headless Chromium under the preview CSP, recording console errors, uncaught exceptions, failed requests, and CSP violations, with a screenshot of each in `.results/screenshots/`. For a game with the hooks, a playthrough clicks `data-rafflex-play` once per entry in `plays` and checks each `data-rafflex-result="win|lose"` revealed matches the predetermined result, in order, and that no plays shows an empty state. A mismatch is the blocking `playthrough_mismatch`. For a game whose template uses images, a buyer images pass swaps every image a buyer may replace for a placeholder of another shape and runs at one phone and one desktop width, saving `.results/screenshots/buyer-images-<device>.png` (`buyer_images` in the JSON). Uncaught exceptions and CSP violations block too; console errors and failed requests are warnings.
* **Your own specs.** `tests/*.spec.mjs` export a test function, or an object of named ones, as the default export. Each receives the kit's helpers: `open(scenario, {width, playCount, options})` (options are values set as a site owner or buyer sets them, coerced as the platform coerces them), `playNext()` (returns `win` or `lose`), `result()`, `results()`, `expected(scenario)`, `screenshot(name)`, `page` (Playwright), and `assert` (`node:assert/strict`). A failure is the blocking `creator_test_failed`.

## The app

`npx @rafflex/dev` serves the Rafflex app for the whole workspace on `127.0.0.1`, and prints three lines: the workspace, the app's address, and "Leave this running. Close it with Ctrl+C."

* **Home:** the Get started prompt for your AI, the AI apps found on this computer with their connect commands, New game and New block, and a health strip (rules, kit version, git).
* **Products:** every product with its version, state (Not pushed yet, Changes not pushed, In review, Changes requested, Rejected, Removed, Live 1.2.0), small badges for open bug reports and unanswered questions, and last test result (Passed, Issues, Not tested).
* **Product** at `/p/<type folder>/<folder>/` (for example `/p/games/spin-to-win/`): when the latest review asked for changes or rejected the version, the reviewer's decision and notes (shown as plain text) with what is still missing and a prompt to fix them, above everything else; badges for open bug reports and unanswered questions, each with a prompt in the menu that has the AI read them through the marketplace's tools (what buyers write never reaches the workspace); one line of installs, sales, and rating for a live product; the preview with scenario, play count, and device controls; Options, the form a buyer sees (the inferred options with the labels, help, and choices from `options.json`), where changing a value renders the preview with it and Reset returns to the defaults (values are remembered per product in this browser); Buyer images, for a game that uses images, which swaps each one a buyer may replace for a placeholder of another shape; Test, which runs `verify` with live progress and shows blocking issues with fix prompts, screenshots, and the playthrough from the product's `.results/`; Get it live, the next step with its prompt (disabled while tests have blocking issues) and a Before review list of what review still needs, such as the cover image and screenshots (it never disables pushing a draft); prompts for changing, fixing, the next version, and reverting; and the Unreleased notes.
* **New product:** a name and a type, which runs `new`, then the prompt to hand to your AI.

Every prompt opens straight in your AI app when the kit finds one that takes a prompt from a link: Claude Code (in the workspace folder), Claude Code in VS Code, Codex in the ChatGPT desktop app, or Cursor. The app fills its prompt box and waits for you to press Enter. **Copy** is always beside it, and the menu offers your other AI apps, a terminal command that starts Claude Code or Codex with the prompt, and the link itself. Claude Code's link works once you have sent it one prompt on this computer.

Everything updates by itself: saving a product's `template.twig`, `options.json`, `product.json`, or anything in its `assets/` reloads only that product's preview, and products your AI adds, tests, or pushes appear and change on their own. Every prompt comes from the marketplace's `/dev-kit/prompts.json`, filled in locally, so the wording improves without a kit release.

The app answers only requests addressed to its own address (no DNS rebinding), every action (new product, test, open folder) needs a random token generated at start and embedded in the page, and every path is checked to resolve inside the workspace. A product's frame and files map reach only its own `assets/` folder. The app holds no account access: publishing stays with your AI.

Files in `assets/` are referenced as `{{ files['tag'] }}`, where the tag is the slugified filename stem (`Win Jingle.mp3` becomes `win-jingle`), the same tag the studio gives an upload. An approved library build (for example the three.js bundle) is recognised by its SHA-256 and loads from its shared URL, byte identical to the live site.

Everything the kit reports is guidance. The marketplace's own check is the final verdict.

## Rules, offline use, and privacy

The kit reads the platform's rules, sample contexts, starter templates, approved libraries, and categories from the marketplace's public `/dev-kit/*.json` endpoints, caches them in the workspace's `.rafflex/cache/`, and works offline from that cache. A rule change on the platform reaches your next run without a kit update. Beyond those GET requests the kit downloads the export bundles, media files, and listing images you `import` (and Playwright with Chromium when you run `test --install`).

The kit sends a product's files only when `push` is given a sync link that the creator's AI requested with `request_sync`, and only to that link's own address on the marketplace this workspace uses and to the upload links the marketplace answers with (on the marketplace or its media address). It never follows a redirect, prints the link with its signature left out, and never writes the link to disk or to git. It has no sign in and holds no secret: the link expires after 15 minutes.

Behind a corporate proxy that inspects HTTPS, set `NODE_EXTRA_CA_CERTS` to the proxy's certificate authority.

## Known differences from the platform renderer

The preview renders with [twig.js](https://github.com/twigjs/twig.js), adjusted to match the platform renderer for the sandboxed subset (string literal escapes, `default` keeping `false`, number printing and `json` encoding, `trim` sides, missing keys being undefined, the newline after a comment). A shared fixture suite proves the two agree. What remains:

* The sandbox whitelist is a lint over the parsed template rather than a runtime sandbox, and twig.js reports some syntax errors with different wording or no line.
* twig.js cannot parse a string literal that ends in an escaped backslash (`'\\'`).
* Joining a boolean with `~` gives `true` or `false` where the platform gives `1` or nothing, and mapping keys that look like integers come first.
* Upload checks recognise images, audio, and 3D models by their first bytes. The platform inspects the content more fully, and accepts an image whose content and extension disagree (a JPEG named `.png`), which the kit refuses so the stored type and the name always match.

## Development

```sh
npm test                 # unit, CLI, server, browser (when Chromium is available), and recorded parity tests
RAFFLEX_BASE_URL=https://marketplace.rafflex.io npm run test:parity
```

The recorded fixtures in `test/fixtures` are regenerated by the Rafflex team from the platform. `node scripts/copy-icons.js` copies the Heroicons the app uses into `src/client/icons` (the app is offline, so icons are bundled, never loaded from a CDN).
